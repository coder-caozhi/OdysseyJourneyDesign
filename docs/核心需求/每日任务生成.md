# 每日任务列表生成

## 1. 产品背景

鸿蒙星空是围绕提升用户留存、增强用户对鸿蒙系统熟悉度与使用粘性而推出的一项元服务。用户通过完成一系列轻量化的日常任务获取能量值奖励，在过程中逐步熟悉鸿蒙系统的各项功能与操作逻辑。

每日任务列表是用户访问最频繁的入口，也是整个任务体系的核心链路——**列表里展示什么任务，直接决定用户当天会做什么**。

核心接口：`GET /getDailyMissions?userId=&appId=`

## 2. 架构定位

```
端侧（鸿蒙设备）
    │
    ▼
旅程服务（API）── Redis（用户任务缓存 + 分布式锁）
    │
    ├── 本地缓存 Caffeine（任务/任务组/奖品等运营配置）
    │
    ▼
MySQL（分库分表：成长记录 + 成长账户快照）
```

运营配置（任务组、任务、奖品）由管理服务维护，旅程服务通过异步线程定时拉取到本地 Caffeine 缓存，生成逻辑**零 RPC 调用**。

### 3.2 执行步骤

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1 | 参数校验 + 白名单校验 | 校验 userId/appId；管理后台可配置灰度白名单，灰度任务仅对白名单用户可见 |
| 2 | 读 Redis 缓存 | key = `mission:daily:{userId}:{appId}`，命中且未跨天则直接返回，无需后续步骤 |
| 3 | 获取分布式锁 | key = `lock:daily:{userId}:{appId}`，超时 10s；获取失败返回友好提示，不自旋 |
| 4 | 加载运营配置 | 从本地 Caffeine 缓存读取全量上架任务组及任务，零网络开销 |
| 5 | 加载用户画像 | 查成长账户（历史快照、里程碑）+ 成长记录（任务完成状态） |
| 6 | 执行生成策略 | 工厂 + 策略模式，按固定顺序跑四种策略直至填满当日配额 |
| 7 | 数据落地 | 事务内：批量 insert 成长记录 → update 账户快照 |
| 8 | 写缓存 + 释放锁 | 缓存 25 小时过期（比自然天多 1 小时防并发穿透） |

### 3.3 关键边界

**缓存命中率 > 95%**：一次生成后 24 小时内所有请求直接读 Redis，生成逻辑只执行一次/用户/天。

**未完成任务继承**：昨日 energy=0 的任务不会消失，新一天直接纳入当日列表，不计入新生成配额，但占据返回位置。这避免了用户已完成一半的任务被"吞掉"。

**跨天判断**：缓存中存 `createTime`，比较日期，跨天则主动失效。

## 4. 策略模式：任务生成矩阵

生成逻辑是整个接口的核心。四种策略通过 `MissionStrategyFactory` 按 **genStrategy** 字段路由，顺序执行：

```
专属任务 → 剩余优先级递增 → 优先级优先 → 随机兜底
```

| 序号 | 策略 | genStrategy | 适用场景 | 核心规则 |
|------|------|-------------|----------|----------|
| 1 | 专属任务生成 | `resident` | 星球里程碑专属任务组 | 根据 isResident 决定是否允许循环；额度 = 日上限 - 未完成数 - (isResident ? 0 : 已完成数) |
| 2 | 剩余优先级递增 | `progressive` | 普通任务组，难度递进 | 过滤"已接触"任务 + 过滤 priority ≤ 历史最高优先级的任务，按 priority 升序取 |
| 3 | 优先级优先 | `priority` | 高价值运营任务 | 排除已接触任务，按 priority 降序取前 N |
| 4 | 随机兜底 | `random` | 配额不满时兜底 | 开放所有上架任务（含已完成的），随机打乱取满剩余配额 |

**关键概念——"已接触"**：任务曾在用户成长记录中出现过（无论完成与否）。当前 energy=0 的不会再生成（策略 4 除外）。

**生成内配额传递**：上下文对象 `GenerateContext` 携带当前剩余配额，策略之间串行扣减。

### 代码骨架

```java
// 策略接口
public interface MissionGenerateStrategy {
    List<MissionDTO> generate(GenerateContext context);
}

// 模板方法抽象类 —— 提取"加载候选 → 自定义筛选"的公共流程
public abstract class AbstractMissionStrategy implements MissionGenerateStrategy {
    @Override
    public final List<MissionDTO> generate(GenerateContext context) {
        if (context.getRemainingQuota() <= 0) return Collections.emptyList();
        List<Mission> candidates = loadCandidates(context);
        return selectByRule(candidates, context);
    }
    protected abstract List<MissionDTO> selectByRule(List<Mission> candidates, GenerateContext context);
}

// 工厂：按任务组 genStrategy 字段路由
@Component
public class MissionStrategyFactory {
    private final Map<String, MissionGenerateStrategy> strategyMap;

    public MissionStrategyFactory(List<MissionGenerateStrategy> strategies) {
        // Spring 自动注入所有实现类，按策略名映射
    }

    public MissionGenerateStrategy getStrategy(String genStrategy) {
        return strategyMap.getOrDefault(genStrategy, randomStrategy);
    }
}
```

## 5. 多级缓存设计

| 层级 | 存储 | 内容 | 过期/刷新 | 命中率 |
|------|------|------|-----------|--------|
| L1 本地 | Caffeine | 任务组、任务、奖品等运营配置 | 异步线程定时全量刷新 | ~100% |
| L2 分布式 | Redis Hash | 用户当日任务列表 + createTime | 25 小时 | > 95% |
| L3 持久层 | MySQL | 成长记录 + 成长账户快照 | 永久 | — |

**缓存穿透防护**：Redis 不存在时走生成流程，生成完成后立即写回；分布式锁保证同一用户只有一个线程执行生成。

**缓存击穿防护**：过期时间 25h > 24h 自然天，同一用户的请求不会同时穿透。

**缓存雪崩防护**：不同用户的 key 过期时间打散在 24-25h 之间，避免批量同时失效。

## 6. 数据一致性

采用"先写记录再写快照"的事务顺序：

```sql
BEGIN;
-- 1. 批量插入新任务记录，energy=0 表示未完成
INSERT INTO t_user_growth_record (user_id, mission_id, energy, create_time, ...)
VALUES (...), (...), ...;
-- 2. 全量更新账户快照（JSON 字段）
UPDATE t_user_growth_account
SET mission_snapshot = ?, update_time = NOW()
WHERE user_id = ? AND app_id = ?;
COMMIT;
```

若 Redis 写缓存失败：事务已提交的数据是最终真实数据，Redis 缺失仅导致下次请求重新生成（幂等），不丢数据。

## 7. 边界与容错

| 场景 | 处理方式 |
|------|----------|
| 新用户（无任何历史记录） | 快照和历史最高优先级均为空，正常走生成流程，相当于从零开始 |
| 所有策略跑完仍不满配额 | 返回实际生成数量，前端可隐藏剩余卡片位 |
| 配置同步延迟 | 本地缓存定时刷新，短暂不一致可接受；管理后台可手动触发立刻刷新 |
| 分布式锁死锁 | 锁超时 10s 自动过期兜底，同时监控异常持锁日志 |
| 生成过程异常 | 事务回滚 + 释放锁 + 返回通用错误码，用户可重试 |
| 同一用户并发请求 | 第一个请求拿锁正常生成，后续请求在锁超时内返回"生成中，稍后重试" |

## 8. 设计亮点

以下可直接用于面试自述或简历项目描述：

1. **二级缓存加速**：运营配置本地化 + 用户任务 Redis 化，接口平均耗时从 ~300ms 降至 15ms 以下
2. **策略模式编排**：四种策略通过工厂动态编排，新增运营策略（如"基于用户标签的个性化推荐"）零侵入现有代码
3. **未完成任务继承**：昨日未完成任务自动纳入今日列表，避免用户进度丢失，任务完成率提升约 12%
4. **分布式锁 + 缓存过期双保险**：锁防并发生成，过期时间 > 24h 防批量穿透，两者配合保证高并发下的数据一致性
5. **白名单灰度能力**：新任务组先推送给测试/众测用户，验证数据后全量上线，降低运营风险
